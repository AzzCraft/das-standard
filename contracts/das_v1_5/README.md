# Edition 1.5 reference contracts

HTTP declaration/inventory contracts are controlled original-byte copies of
the sole protocol authors. The native offline probe projects locked OpenAPI
operations/security, retaining source identities and coverage unknown; it is
not full schema validation, approved facts or actual authorization. The separate
loopback reference joins the existing durable resource boundary. Final installed
qualification remains open; the current inventory has 37 reference schemas.

These schemas are **reference contracts, not approval or qualification**. They
describe the implemented preview, signature-binding probe, committed candidate,
version-switch and integration/Completion staging, action grant and bounded
text-delta exchanges. Native signed evidence/action-Decision consumption is
implemented for the explicit all-attempts-pass/no-reuse reference profile.
The installed current-facts resolver now creates a scope/candidate/policy-bound
Bundle and a read-only Context Pack with the full requirement trace. The current
3.0.0 catalog has complete leaf mapping, separately from qualification. Complete
determined inputs can prepare adoption and bind the actual Standard snapshot,
approved facts and Bundle into the existing verification/CAS/Completion chain.
Finite TEST protected replacement and original-byte collection are implemented;
remaining variants, approved collector/signer deployment, full compatibility and
final installed qualification remain unfinished. The new Completion
contract records a real staging transaction; it does not qualify beta or activate
a deployment. Successful schema validation never grants permission.

The single authors are the files in `schemas/das_v1_5` of
`cadence-oss/cadence-protocol`. This directory contains byte-identical generated
copies. The Standard manifest records each identity, local path and SHA-256 in
`extensions.referenceContracts`; its release snapshot binds these bytes. This
metadata states content provenance and closure, not a trusted signature or a
publication event. The schemas are supporting artifacts and do not add a
requirement to deploy a named tool.

In the joint source workspace, edit the protocol author and run its exact
contract tests. Then run `cadence-oss/tools/generate_contract_copies.py` to update
all consumers and this inventory, followed by the Standard content-snapshot
generator. Do not edit a copied schema to make a test pass. The same generator's
`--check` compares source and copies without changing files. It is a development
workspace tool and is not required in the exported Standard repository.

The standalone `scripts/verify --full` checks all 37 identities and digests,
required-artifact membership, schema syntax and local reference closure using
the existing pinned verification dependencies. It rejects external schema
retrieval, unresolved references, duplicate schema fields and identity changes.
It needs no companion checkout, network, candidate code or private trust root.
The existing release allowlist carries this directory with the validator,
manifest and snapshot. Verify the actual exported tree, not only this workspace.

The runtime contract remains stricter than ordinary JSON Schema validation:
exact safe integers, native DSSE payload bytes and purpose, trusted identities,
current authority, nonreplayable state and complete candidate bindings must be
checked by the relevant consumers. The public signature probe accepts supplied
control context and emits an unapproved preview. Neither these copies nor an
internally recomputed hash can establish independent trust; final installed
artifacts must match the separately approved release identity.

The three new plan/evidence/Decision schemas preserve the approved denominator,
original run/attempt/report/artifact identities, whole C/B/I/task/policy/tool
context and separate action/target/receipt bindings. Core consumes actual DSSE
PAE bytes under the expected purpose and scoped original-byte reader; dasops can
install that same pinned native consumer at its SQL commit predicate. Supplying
TEST context or passing `contracts check-action --probe` is not deployment
approval. Native receipt/Completion authority and qualification remain false.

Completed-task reverification reuses those unpublished Edition 1.5 reference
schemas and the separate analysis schemas below. A verification-only plan has
exactly `actions=["audit"]`; its bindings add the paired `completionDigest` and
`verificationScopeDigest`. The first hashes the retained original native Completion
bytes. The second is the existing canonical digest of the complete audit intent
with only `parameters.verificationPlanDigest` omitted to avoid a circular hash.
The signed action grant separately binds the full original intent, including that
plan digest. Both bindings must be checked. Neither digest substitutes for the
other. The lineage digest also retains the explicit nonmaterial revision mappings.
Audit bindings or Decisions cannot authorize integrate/complete/apply/rollback.

The installed independent verifier consumes a current `audit` grant with
`leaseGeneration=0`, its own principal, exact task/resource/target/request and
reserved budget. Zero means this explicit service profile has no Worker lease;
it never grants a business operation or renews the old lease. Other actions still
require positive generations. Earlier legal audit grants with positive generations
remain readable but do not satisfy this installed profile. The existing native
DSSE/report/history consumer verifies current audit evidence and original bytes
at the same SQL record boundary, including final grant and freshness rechecks.
Execution occurs outside that transaction in the approved test space; retries do
not redispatch. Results reference the original Completion and leave its bytes,
parent/task/cycle/target and prior receipts unchanged. Failure retains spent cost.

Earlier legal reference records keep their prior validation and digest semantics.
New audit records require these updated readers; no claim is made that an older
reader accepts the new fields/actions. This pre-release reference addition is not
a change to a published stable contract, deployment approval or release evidence.

The five `das-analysis-*/v1` contracts implement the separate, preapproved
analysis path from A01.2. The task binding fixes analysis mode and the check
scope at task creation, before a worker claim. Plan, evidence and Decision use
the same native original-report and full-run-history consumer, with separate
DSSE payload types; an integration envelope cannot be relabeled as analysis.
The analysis Completion has no integrated candidate or integration receipt.
Its exact request, shared budget and unique task/cycle record commit together
in the existing SQLite database, without changing the shared target. The
immutable creation event and current full task/candidate/baseline bindings are
rechecked before writing. Existing tasks cannot opt out of integration later.
An explicit rework retains the original completion and starts a new cycle.
That cycle needs a fresh independent binding approved at rework, before a new
worker claim; missing approval or an older cycle's Decision cannot complete it.
Rework cannot turn an original integration task into an analysis task.

Three `das-version-*/v1` plan/evidence/Decision identities cover the original
protected-reference apply/rollback profile. Their exact bindings include the
version plan digest, actual before/after candidate, task obligation, generation
and rollback lineage. They share the original native report/history consumer;
their DSSE purposes cannot substitute for integration or analysis. Each switch
requires its current purpose-specific business grant. Rollback checks the
retained forward receipt and matching current postimage/generation at commit.
It advances generation and retains original audit/budget/receipt history; it
does not undo Completion or cover arbitrary live-directory writes.

The facts-check reference preserves the exact DSSE payload-byte digest, canonical
payload/envelope/current-context digests and distinct native signer/key identities. Only
the order of verified fact records is normalized for approvedFactsDigest; scope,
generation, validity, policy, catalogs and target remain part of that digest. Its
public CLI output has authority=false and qualification=false. Only an installed
service's authenticated current loader can establish Bundle applicability; the
request cannot install keys, a control loader or an executable. Bundle
authorityVerified describes that facts boundary, never permission to act, a
conformance PASS or a completed task. Context Pack remains a reading view.
Unknown/conflict obligations are included; false rows remain in the full trace.
The adoption consumer recomputes through the installed resolver, rejects changed
inputs and incomplete applicability/migration, and does not invoke the legacy
file normalizer. Candidate replacement and current action approval retain their
original protected resource boundary. Production activation is still disabled.

Complete mapping uses new closed identities: `das-bundle-preview-input/v3`,
`das-bundle-preview/v3`, `das-approved-facts-check/v2`,
`das-bundle-resolution/v2` and `das-context-pack/v2`. The earlier preview/v2
keeps its partial-mapping contract; it cannot consume the full 3.0.0 catalog.
Unsupported catalog/output combinations reject. The new Bundle requires the
physical StandardRef; resolving every leaf grants neither an action nor a PASS.

The development adoption bridge prepares native-verified originals outside the
writer transaction. At its existing bounded commit predicate it requires the
same signed originals, catalogs, keys/principals/threshold, current policy,
revocations, generations, actor/scope/target and physical Standard bytes. Only
fresh valid observation times may change. Changed originals require a new
native preparation before entering the writer. The resolver retains only its
latest exact preparation in memory; close, unsuccessful/unresolved preparation
or another preparation invalidates its earlier use. There is no persisted allow.
The original two-second qualification deadline covers this confirmation, grant
and evidence consumption together. This explicit development profile uses the
raw snapshot digest as standardDigest; it does not stand for a distribution
archive digest, production signing subject or final installed acceptance.

New installed Bundle producers require a normalized absolute Standard root and
an independently provided SHA-256 of the RAW `release_snapshot_manifest.json`
bytes. The existing non-circular content format binds every declared required
member, VERSION/manifest edition, and the actual module/requirement catalogs.
Reads use directory handles without following links or running package scripts;
missing/changed content, writable/shared members, unsafe paths and exceeded
limits reject. All members are checked before and after native work within the
same five-second budget, outside the database writer. Unlisted files are never
used as Standard content or executed.

`standardRef.snapshotDigest` binds the raw snapshot; `contentDigest` binds its
sorted member inventory. Both enter the stable Bundle subject. The optional
field preserves prior reference-record reading and its original hash algorithm;
an old record is never a substitute for current producer/adoption recomputation.
The installer must preserve the approved object/digest domain of `standardDigest`
and prove its mapping to this raw snapshot/member closure. Distribution bytes,
raw snapshot bytes, canonical JSON and content inventory are distinct digest
domains; this reader does not verify a distribution archive or activate it.
This content check does not complete leaf
semantics, activation/channel/rollback policy, production installation or
release approval. TEST pins calculated from source establish no such approval.

bundleDigest identifies the approved inputs, resolver and derived applicability;
equivalent fact order and refreshed observation time leave it stable. recordDigest
also binds the exact signature envelope, payload bytes and current observation.
Both are content-integrity checks, not independent authority. A format validator
checks the nested native preview and both Bundle hashes, without certifying trust.
The service reads current inputs in short read-only snapshots of its existing
database before and after native work; it retains no writer lock during resolution.
Action-time authorization and original target transactions remain separate.
